## Notas

- El mensaje 12.1 (`ExportarReporte(tipo, formato, filtros)`) sugiere un **unico endpoint generico** que recibe el tipo de reporte como parametro, pero en el codigo real hay **5 endpoints de exportacion separados** (`/reportes/ventas/exportar`, `/asistencia/exportar`, `/inventario/exportar`, `/productos/exportar`, `/reservas/exportar`), uno por cada pantalla de reporte, todos reusando los mismos [`exportar_csv()`](/backend/app/core/exportar.py#L13)/[`exportar_excel()`](/backend/app/core/exportar.py#L25). El "tipo" de reporte esta fijado en la URL, no es un parametro de un endpoint compartido.
- Este diagrama solo modela **2 de los 5 reportes** que existen realmente bajo CU16: Ventas (mensajes 6-8) e Inventario (mensajes 9-11). Tambien existen, con el mismo patron consulta+exportar, el reporte de **Asistencia de empleados** (horas conectadas, derivadas de pares LOGIN/LOGOUT en `bitacora` -- reusa el mismo log de auditoria que CU01/CU17, sin tabla propia), el de **Productos mas vendidos** (ranking configurable ascendente/descendente) y el de **Reservas** (tasa de conversion a venta).
- El "PDF" mencionado en el comentario del archivo ([reportes.py:41](/backend/app/api/v1/endpoints/reportes.py#L41)) no es un formato que genere el backend: se resuelve enteramente en el frontend con [`imprimir()`](/frontend/src/app/pages/admin/reportes/ventas/ventas.ts#L105) (`window.print()` sobre la misma vista HTML) -- el backend solo produce JSON, CSV y Excel.
- El mensaje 3 (`CalcularReservasActivasYClientesNuevos`) esta dibujado hacia "BD : Ventas" como los demas KPIs del dashboard, pero en realidad consulta las tablas `reserva` y `usuario`, no `venta`/`pago` -- el diagrama agrupa todas las fuentes de datos del dashboard bajo un solo actor de base de datos por simplicidad.
- Todos los reportes comparten el mismo default de rango de fechas via [`_rango_fechas()`](/backend/app/api/v1/endpoints/reportes.py#L45): si no se especifica `fecha_desde`/`fecha_hasta`, se usan los ultimos 30 dias -- detalle no visible en los mensajes del diagrama, que muestran los filtros como si siempre vinieran completos.
- Este es el unico CU de todos los documentados hasta ahora que **no usa ningun stored procedure**: todas las consultas son SQL crudo armado con `text()` directamente en el endpoint (agregaciones `SUM`/`COUNT`/`GROUP BY`), consistente con que este CU es de solo lectura (no hay inserciones ni `log_bitacora()` en ningun endpoint de `reportes.py`).
