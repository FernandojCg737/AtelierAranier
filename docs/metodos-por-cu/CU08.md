## Metodos por clase/objeto

**Frontend : Catalogo** ([`catalogo.ts`](/frontend/src/app/pages/admin/catalogo/catalogo.ts))
- [`loadSucursales()`](/frontend/src/app/pages/admin/catalogo/catalogo.ts#L108) -- filtra client-side a la sucursal propia si el usuario no es administrador, y selecciona automaticamente la primera visible
- [`seleccionar(sucursal)`](/frontend/src/app/pages/admin/catalogo/catalogo.ts#L82) -- usa un cache en memoria (`Map`) por `sucursal.id`, no vuelve a pedir el catalogo de una sucursal ya consultada

**Backend : Catalogo** ([`catalogo.py`](/backend/app/api/v1/endpoints/catalogo.py))
- [`list_sucursales_catalogo(db, _usuario)`](/backend/app/api/v1/endpoints/catalogo.py#L13) -- `GET /catalogo/sucursales`
- [`list_catalogo_sucursal(sucursal_id, db, usuario)`](/backend/app/api/v1/endpoints/catalogo.py#L21) -- `GET /catalogo/sucursales/{id}/productos`

**Base de Datos : Sucursal** (tabla `sucursal`, modelo [`Sucursal`](/backend/app/models/p2_clientes.py))
- Listado completo ordenado por nombre (mensaje 2)
- Verificacion de existencia por `id` (mensaje 5)

**Base de Datos : Producto** (tabla `producto`, modelo [`Producto`](/backend/app/models/p3_catalogo.py))
- `JOIN` con `Inventario` filtrando `estado == "activo"` y `sucursal_id`, con `joinedload` de marca/categoria/imagenes/inventarios(talla,color), lineas [37-51](/backend/app/api/v1/endpoints/catalogo.py#L37)

**Base de Datos : Inventario** (tabla `inventario`, modelo [`Inventario`](/backend/app/models/p3_catalogo.py))
- Los registros de inventario de la sucursal ya vienen incluidos en la consulta del mensaje 6 (via `joinedload`); no hay una segunda consulta a la base de datos para el mensaje 7.

## Notas

- El mensaje 7 (`ObtenerCantidadPorVariante`) esta modelado en el diagrama como una consulta separada a `BD : Inventario`, pero en el codigo real **no existe una segunda query**: los inventarios ya se trajeron junto con los productos en la consulta del mensaje 6 (gracias a `joinedload(Producto.inventarios)`), y la suma de `cantidad_total` (linea [56](/backend/app/api/v1/endpoints/catalogo.py#L56)) es una operacion en memoria sobre esos datos ya cargados, no un nuevo `SELECT`.
- El control de acceso por sucursal (CU08/CU12: Encargado/Cajero solo ven su propia sucursal, Administrador ve todas) esta implementado **dos veces**, y el diagrama no muestra ninguna: (a) en el frontend, [`loadSucursales()`](/frontend/src/app/pages/admin/catalogo/catalogo.ts#L114) filtra la lista de sucursales antes de mostrarla; (b) en el backend, [`list_catalogo_sucursal()`](/backend/app/api/v1/endpoints/catalogo.py#L34) devuelve `403 Forbidden` si el `usuario` no es administrador y pide una sucursal que no es la suya -- segun el comentario en el codigo, este chequeo de backend se agrego porque antes la API aceptaba cualquier `sucursal_id` aunque el frontend lo ocultara.
- La seleccion de sucursal (mensajes 4/4.1) usa un **cache en memoria por sucursal** en el frontend ([`seleccionar()`](/frontend/src/app/pages/admin/catalogo/catalogo.ts#L87)): si el usuario vuelve a hacer click en una sucursal ya consultada, no se repite el mensaje 4.1 hacia el backend -- comportamiento de UX no representado en el diagrama.
- `loadSucursales()` tambien dispara automaticamente el mensaje 4/4.1 para la primera sucursal visible apenas termina de cargar la lista (linea [117](/frontend/src/app/pages/admin/catalogo/catalogo.ts#L117)) -- en la practica, los mensajes 1-3 y 4-8 no son dos interacciones separadas del usuario sino que la segunda ocurre automaticamente tras la primera, salvo que el usuario elija otra sucursal despues.
