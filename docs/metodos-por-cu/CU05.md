## Notas

- El diagrama muestra `BuscarProducto()` y `ObtenerProductoCreado()/ObtenerProductoActualizado()` como mensajes separados, pero en el codigo real es la **misma funcion** [`_get_producto_or_404()`](/backend/app/api/v1/endpoints/productos.py#L111) reutilizada en los tres flujos (alta, edicion, subir imagen): valida que el producto existe y trae todas sus relaciones (categoria, marca, proveedor, temporada, coleccion, imagenes, inventarios) via `joinedload`.
- El alta de producto (mensajes 1-5) **no incluye imagenes ni estado inicial**: `estado` no forma parte de `ProductoCreate`, solo de `ProductoUpdate` (mensaje 6.1) -- un producto recien creado queda con el estado por defecto de la base de datos, y recien se le pueden subir imagenes despues de creado (mensajes 12-17), porque `add_imagen()` necesita un `producto_id` ya existente.
- El diagrama simplifica "RegistrarActualizacion(ACTUALIZAR)" (mensaje 16) como si fuera un evento distinto de "RegistrarEdicion" (mensaje 10), pero ambos son la misma llamada a [`log_bitacora()`](/backend/app/core/audit.py#L36) con `accion="ACTUALIZAR"` -- solo cambia el `detalle` del mensaje ("Edicion de producto..." vs "Se agrego una imagen a...").
- El frontend permite subir **varias imagenes a la vez** ([`onFileSelected()`](/frontend/src/app/pages/admin/productos/productos.ts#L277)), pero las envia con un `POST` separado por archivo (uno a la vez, en un `for...of`), no en un unico request multipart con varios archivos -- el diagrama modela un solo mensaje `SubirImagen(archivo)` que en la practica se repite N veces.
- `toggleEstado()` (linea [251](/frontend/src/app/pages/admin/productos/productos.ts#L251)) tambien llama a `update_producto()` (reenviando todos los campos actuales mas el `estado` invertido) para activar/desactivar un producto -- no aparece en este diagrama pero usa exactamente el mismo endpoint que el mensaje 6.1.
