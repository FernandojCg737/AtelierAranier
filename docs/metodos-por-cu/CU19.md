**Servicio Externo : Gemini AI**
- `POST /v1beta/models/gemini-3.6-flash:generateContent` (redacta la respuesta del bot, usando solo el contexto real que le manda el backend)

**Base de Datos : Chatbot** -- en realidad **dos tablas** agrupadas bajo un solo bubble en el diagrama:
- `chatbot` (tabla `Chatbot`, una fila por sesion/conversacion, con `fecha_inicio`/`fecha_fin`)
- `chatbot_mensaje` (tabla `ChatbotMensaje`, una fila por mensaje, `remitente` = `"cliente"` o `"bot"`)
- El mensaje 4 (`ConstruirContexto`) en realidad no toca estas tablas: consulta `sucursal`, `producto`/`categoria`/`marca` e `inventario` (ver Notas)

## Notas

- El mensaje 4 (`ConstruirContexto(sucursales, productos, inventario)`) esta dibujado hacia "BD : Chatbot" como los demas mensajes de persistencia, pero [`_construir_contexto()`](/backend/app/api/v1/endpoints/chatbot.py#L72) en realidad consulta `sucursal`, `producto`/`categoria`/`marca` e `inventario` -- **ninguna de esas es la tabla `chatbot`/`chatbot_mensaje`**. El diagrama agrupa todas las fuentes de datos del backend bajo un solo actor de base de datos, mismo patron de simplificacion que ya se documento en CU16 y CU18.
- [`_get_or_create_sesion()`](/backend/app/api/v1/endpoints/chatbot.py#L38) (mensaje 2) tiene una logica de continuidad que el diagrama no distingue: si la sesion mas reciente del cliente tuvo actividad (ultimo mensaje o inicio de sesion) hace **3 horas o menos** (`_UMBRAL_NUEVA_SESION`), se reutiliza esa misma sesion; si paso mas tiempo, se cierra la sesion vieja (`fecha_fin`) y se crea una nueva. Asi el panel de administracion ve conversaciones separadas por corte de inactividad, no un chat infinito por cliente.
- El historial que se le manda a Gemini (mensaje 5) excluye el mensaje que el cliente acaba de mandar (`[:-1]` en la linea [157](/backend/app/api/v1/endpoints/chatbot.py#L157)): ese mensaje ya se pasa por separado como el parametro `mensaje`, para no duplicarlo dentro de `historial`.
- El dictado por voz (boton de microfono) y que el bot conteste hablado se resuelven **enteramente en el navegador** con la Web Speech API (`SpeechRecognition`/`window.speechSynthesis`, lineas [140-182](/frontend/src/app/components/chatbot-widget/chatbot-widget.ts#L140)) -- no hay ningun mensaje ni endpoint de backend involucrado; dictar una pregunta produce exactamente el mismo mensaje 1.1 que escribirla.
- [`generar_respuesta_chat()`](/backend/app/core/gemini.py#L40) nunca falla de forma visible para el cliente: si no hay `GEMINI_API_KEY` configurada o la llamada lanza cualquier excepcion, devuelve una disculpa generica fija (`_RESPUESTA_SIN_IA`) en vez de propagar un error -- mismo patron de respaldo que CU18 (Gemini nunca es un punto de fallo duro).
- `_construir_contexto()` decide que productos incluir con un match simple de **palabras clave** (`_palabras_clave()`, quitando `_STOPWORDS` como "que"/"hola"/"gracias") contra nombre/descripcion/categoria/marca -- no es busqueda semantica ni vectorial, es coincidencia de substring en Python sobre los productos activos.
- `mis_mensajes()` (`GET /chatbot/mias`) no aparece en este diagrama: es lo que carga [`ChatbotService.cargar()`](/frontend/src/app/services/chatbot.ts#L24) al abrir el widget por primera vez, para mostrar la conversacion previa antes de que el cliente escriba un mensaje nuevo.
