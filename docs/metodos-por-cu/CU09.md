## Notas

- El diagrama modela "Frontend : ProbadorAR" y "Backend : ProbadorAR" como un solo objeto cada uno, pero en el codigo real son **tres componentes de Angular** ([`ArTryon`](/frontend/src/app/components/ar-tryon/ar-tryon.ts) para el modo en vivo, [`ArFoto`](/frontend/src/app/components/ar-foto/ar-foto.ts) para el modo foto, [`AdminArUso`](/frontend/src/app/pages/admin/ar-uso/ar-uso.ts) para el historial) y **tres archivos de backend** ([`productos.py`](/backend/app/api/v1/endpoints/productos.py) para los endpoints AR, [`core/decart.py`](/backend/app/core/decart.py) como cliente HTTP de Decart, [`ar_uso.py`](/backend/app/api/v1/endpoints/ar_uso.py) para el listado de uso).
- Los mensajes 6, 7 y 8 (`ConectarWebRTC`, `EnviarImagenReferencia`, `TransmitirVideoTransformado`) son la **unica parte de este CU que no pasa por el backend propio**: el frontend habla directo con Decart usando el token efimero (via el SDK `@decartai/sdk`), por diseno -- el backend solo entrega el token de corta duracion (600s, con `maxSessionDuration` de 200s impuesto por el propio Decart) para no exponer la API key permanente.
- El modo VIRTUAL (`ArFoto`) en realidad manda un **video corto generado a partir de la foto**, no la foto en si: `enviar_trabajo_foto_ar()` normaliza la imagen a JPEG y la convierte a un clip de 1 segundo con `ffmpeg` ([`_convertir_foto_a_video()`](/backend/app/core/decart.py#L106)) porque el modelo en modo cola (`lucy-vton-3.5`) rechaza imagenes fijas -- el diagrama simplifica esto como `EnviarTrabajoGeneracion(video, ...)`, que ya anticipa correctamente que es un video, pero no muestra la conversion.
- De forma simetrica, el resultado de la generacion tambien vuelve como video: [`obtener_resultado_trabajo_foto()`](/backend/app/core/decart.py#L220) detecta si el `content-type` es `video/*` y extrae un solo frame con `ffmpeg` ([`_extraer_frame_de_video()`](/backend/app/core/decart.py#L199)) antes de devolver la "foto" al cliente -- tampoco visible en el diagrama.
- `RegistrarUsoAR` (mensajes 4 y 12) se registra **al iniciar el intento, no al terminar la generacion**: en el modo ONLINE se guarda apenas se crea el token (antes de que el frontend siquiera intente el WebRTC); en el modo VIRTUAL se guarda apenas Decart acepta el trabajo en cola (antes de saber si esa generacion va a terminar bien o mal). Esto es intencional segun el comentario en [`_registrar_uso_ar()`](/backend/app/api/v1/endpoints/productos.py#L293): lo que se audita es "quien probo que prenda", no si la IA genero un buen resultado.
- `_resolver_imagen_referencia()` (mensajes 2/10) tiene una regla de fallback no visible en el diagrama: si el producto no tiene una imagen AR dedicada (`prenda_ar`), usa la primera foto de catalogo del producto **solo si es una URL absoluta** (`http(s)://`) -- las fotos placeholder con ruta relativa de antes de conectar el backend real se ignoran en vez de mandarse rotas a Decart.
