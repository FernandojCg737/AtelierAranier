## Notas

- El diagrama modela un unico actor "Usuario(Cliente, Administrador, Encargado, Cajero)" y una sola pantalla "Frontend : Perfil", pero en el codigo real existen **dos componentes Angular distintos** con la misma logica duplicada: [`perfil.ts`](/frontend/src/app/pages/perfil/perfil.ts) (pantalla de cliente, con tabs de reservas/compras/etc. que no son parte de este CU) y [`admin/perfil.ts`](/frontend/src/app/pages/admin/perfil/perfil.ts) (pantalla simplificada para staff). Ambos llaman exactamente a los mismos metodos de `Auth`.
- El mensaje 2 (`ActualizarDatosPerfil`) esconde una bifurcacion real que el diagrama no muestra: si `usuario` es instancia de `Cliente` se llama `sp_actualizar_cliente_perfil` (incluye telefono/direccion); si es staff se llama `sp_actualizar_usuario_nombre` (solo nombre) -- ver [`actualizar_perfil()` lineas 31-40](/backend/app/api/v1/endpoints/perfil.py#L31).
- El cambio de password genera un `session_id` nuevo (linea [60](/backend/app/api/v1/endpoints/perfil.py#L60)) precisamente para invalidar cualquier sesion vieja que pudiera estar comprometida -- por eso el mensaje 11 devuelve un `nuevoToken`: el token anterior deja de ser valido de inmediato porque ya no coincide con el `session_id` guardado.
- El aviso de cambio de contrasena por correo (mensaje 10) esta envuelto en `try/except` (linea [87](/backend/app/api/v1/endpoints/perfil.py#L87)): si el envio falla, el cambio de password **no se revierte**, solo se loguea el error -- camino de excepcion no mostrado en el diagrama.
- `require_permiso_cliente("CU15")` es la misma dependencia de autorizacion para ambos endpoints; a pesar del nombre, permite tanto a clientes como a staff con el permiso `CU15` asignado -- es el mismo mecanismo de permisos granulares documentado en CU02.
