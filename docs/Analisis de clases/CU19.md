# CU19 - Atender Cliente con Chatbot (Diagrama de Analisis de Clases)

Correspondencia entre el diagrama de clases de analisis `DAC19` (patron Boundary-Control-Entity) y la implementacion real. Complementa `docs/metodos-por-cu/CU19.md` (diagrama de comunicacion, de comportamiento) con la vista estatica: atributos y firmas de operaciones por clase.

## Atributos por clase

**«Entidad» Chatbot** -- coincide con el modelo real [`Chatbot`](/backend/app/models/p5_analitica.py#L113) 1:1: `canal`, `cliente_id`, `fecha_fin`, `fecha_inicio`, `id`.

**«Entidad» ChatbotMensaje** -- coincide con el modelo real [`ChatbotMensaje`](/backend/app/models/p5_analitica.py#L128) 1:1: `chatbot_id`, `fecha`, `id`, `mensaje`, `remitente`.

## Notas

- **Hallazgo mas notable**: `ConstruirContexto(clienteId)` declara `clienteId` como parametro, pero la funcion real, [`_construir_contexto(db, mensaje)`](/backend/app/api/v1/endpoints/chatbot.py#L72), **no recibe ningun id de cliente en absoluto** -- arma el contexto (sucursales, metodos de pago, productos relevantes con su stock) exclusivamente a partir del **texto del mensaje** ([`_palabras_clave()`](/backend/app/api/v1/endpoints/chatbot.py#L67), coincidencia de palabras clave contra el catalogo), sin importar quien sea el cliente que pregunta. Es una discrepancia de firma concreta, no solo una omision de parametros adicionales como en otros hallazgos de la serie.
- `EnviarMensaje(mensaje, clienteId)` tampoco recibe `clienteId` como parametro real -- [`enviar_mensaje()`](/backend/app/api/v1/endpoints/chatbot.py#L139) lo obtiene de la sesion autenticada (`Depends(require_permiso_cliente("CU19"))`), mismo patron ya visto en `AprobarPagoQR`/`empleadoId` (CU11) y en varios otros controles de esta serie: el identificador del actor nunca se manda explicito, se deriva del token.
- `ObtenerOCrearSesion(clienteId)` no distingue la logica de continuidad real de [`_get_or_create_sesion()`](/backend/app/api/v1/endpoints/chatbot.py#L38): si la sesion mas reciente del cliente tuvo actividad hace 3 horas o menos (`_UMBRAL_NUEVA_SESION`), se reutiliza; si no, se cierra (`fecha_fin`) y se crea una nueva -- mismo hallazgo ya documentado en `docs/metodos-por-cu/CU19.md`, confirmado ahora tambien ausente de la firma en la vista estatica.
- `GuardarMensaje(...)` se ejecuta en realidad **dos veces por cada interaccion**: una para el mensaje del cliente (linea [148](/backend/app/api/v1/endpoints/chatbot.py#L148)) y otra para la respuesta del bot (lineas [162-163](/backend/app/api/v1/endpoints/chatbot.py#L162)) -- el diagrama modela una sola operacion generica para ambos casos, sin stored procedure detras en ninguno de los dos.
- [`mis_mensajes()`](/backend/app/api/v1/endpoints/chatbot.py#L170) (`GET /chatbot/mias`, usado para cargar el historial al abrir el widget por primera vez) no aparece en ningun lado de este diagrama de clases -- mismo alcance ya documentado en `docs/metodos-por-cu/CU19.md`.
- El dictado y la respuesta por voz (Web Speech API del navegador) no corresponden a ninguna operacion de este diagrama -- consistente con que se resuelven enteramente en el frontend, sin tocar ni backend ni entidades.
- `GenerarRespuestaChat(...)` (Gemini) se invoca solo desde el backend, mismo patron ya visto en CU18 -- a diferencia de CU09 (Decart AI), donde el servicio externo si tenia un origen de llamada dual (frontend y backend).
