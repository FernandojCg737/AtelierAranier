# CU10 - Solicitar y Administrar Reservas (Diagrama de Secuencia)

Metodos identificados a partir del diagrama de secuencia `DSC10`, mapeados contra su implementacion real. ## Notas

- **Confirmacion final (tercer diagrama de este CU) de que no hay stored procedures reales** salvo `sp_vencer_reservas_expiradas()` (mensaje 22): `insertarReserva`, `insertarDetalle`, `retenerStock`/`liberarStock` y ambos `actualizarEstado` (mensajes 17 y 31) son todos asignaciones ORM o funciones Python puras -- mismo hallazgo ya establecido en `docs/metodos-por-cu/CU10.md` y `docs/Analisis de clases/CU10.md`.
- A diferencia de los `break [para cada sucursal]` de `CU08.md`/`CU12.md` (que no correspondian a ningun bucle real sobre multiples sucursales en un mismo request), los `break [para cada item de la reserva]` del **Flujo 1** si representan bucles reales: [`crear_reserva()`](/backend/app/api/v1/endpoints/reservas.py#L154) itera genuinamente sobre `payload.items` dos veces (una para validar stock, otra para insertar detalles y retener stock).
- El segundo `break [para cada detalle de la reserva]` del **Flujo 2** esta mal ubicado: envuelve el mensaje 18 (`registrarAccion`), pero `log_bitacora()` se ejecuta **una sola vez** por cancelacion, sin importar cuantos items tenga la reserva. El bucle real por detalle esta dentro de [`_mover_stock_reserva()`](/backend/app/api/v1/endpoints/reservas.py#L117) (mensaje 16), que si itera sobre `reserva.detalles` para liberar el stock de cada uno.
- El mensaje 15 (`mostrarError`) solo cubre el camino `400` ("ya no se puede cancelar"); el codigo real de [`cancelar_mi_reserva()`](/backend/app/api/v1/endpoints/reservas.py#L231) tiene un **segundo chequeo** que el diagrama no modela: `403 Forbidden` si `reserva.cliente_id != usuario.id` (lineas [238-239](/backend/app/api/v1/endpoints/reservas.py#L238)), es decir, si el cliente intenta cancelar una reserva que no es suya.
- El `opt [nuevoEstado = cancelada]` del **Flujo 4** encuadra los mensajes 27-30, pero en el codigo real solo el mensaje 30 (`liberarStock`) es condicional a que `payload.estado == "cancelada"` -- el resto (buscar la reserva, mensaje 28-29) se ejecuta siempre, sea cual sea el nuevo estado.
- `_mover_stock_reserva()` usa `SELECT ... FOR UPDATE` para bloquear la fila de inventario mientras la modifica (evita condiciones de carrera entre reservas simultaneas) -- detalle de concurrencia que ningun mensaje del diagrama distingue explicitamente.
