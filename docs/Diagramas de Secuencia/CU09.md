## Objetos (lineas de vida) y su correspondencia real

- **:FrontendProbadorAR** -> [`ArTryon`](/frontend/src/app/components/ar-tryon/ar-tryon.ts) (ONLINE) + [`ArFoto`](/frontend/src/app/components/ar-foto/ar-foto.ts) (VIRTUAL)
- **:FrontendUsoAR** -> [`AdminArUso`](/frontend/src/app/pages/admin/ar-uso/ar-uso.ts)
- **:GestorProbadorAR** -> repartido entre [`productos.py`](/backend/app/api/v1/endpoints/productos.py), [`core/decart.py`](/backend/app/core/decart.py) y [`ar_uso.py`](/backend/app/api/v1/endpoints/ar_uso.py)
- **p:Producto**, **u:UsoArPrenda** -> tablas `producto`/`uso_ar_prenda`
- **decart:DecartAI** -> servicio externo, llamado **desde dos origenes distintos** (backend y frontend), ver Notas

## Notas

- **`decart:DecartAI` es la unica linea de vida externa de toda la serie de secuencia que recibe mensajes de dos origenes distintos**: `:GestorProbadorAR` (mensajes 6, 18, 23, 27, desde el backend) y `:FrontendProbadorAR` directamente (mensajes 10-12, via el SDK `@decartai/sdk` en el navegador). Confirma por tercera vez (comunicacion, clases, secuencia) la arquitectura hibrida ya documentada: el modo ONLINE conecta el navegador directo con Decart usando el token efimero, sin pasar el streaming por el backend.
- El mensaje 14 (`obtenerImagenReferencia`, rama VIRTUAL) **no tiene un `opt` de error equivalente** al mensaje 5 de la rama ONLINE, aunque el codigo real hace exactamente la misma validacion (`if producto is None or imagen_url is None: raise HTTPException(404, ...)`, lineas [348-352](/backend/app/api/v1/endpoints/productos.py#L348) de `crear_ar_foto()`) -- una asimetria entre como el diagrama representa el mismo chequeo en las dos ramas del `alt`.
- Los mensajes 16-17 (`normalizarFotoAJpeg`, `convertirFotoAVideo`) se dibujan como autollamadas de `:GestorProbadorAR`, pero en el codigo real ambas se ejecutan **dentro de** [`enviar_trabajo_foto_ar()`](/backend/app/core/decart.py#L145) (`core/decart.py`), no directamente en el endpoint `crear_ar_foto()` -- una capa de anidamiento mas de la que el diagrama muestra, aunque el orden secuencial si es fiel al real.
- `RegistrarUso` (mensajes 8 y 20) se ejecuta **antes** de devolver la respuesta al frontend en ambas ramas, apenas el backend logra el paso critico (crear el token en ONLINE, encolar el trabajo en VIRTUAL) -- coherente con el hallazgo ya documentado en `docs/metodos-por-cu/CU09.md`: se audita "quien probo que prenda" al iniciar el intento, no al terminar la generacion.
- El fragmento `break [hasta que el trabajo este listo]` representa el polling real de [`ArFoto`](/frontend/src/app/components/ar-foto/ar-foto.ts#L154) (`setInterval` cada `POLL_MS` = 2500ms) -- a diferencia del uso de `break` en `CU08.md`/`CU12.md` (donde representaba una iteracion "para cada sucursal", uso semanticamente dudoso), aca "salir del bucle cuando la condicion se cumple" esta mas cerca del sentido original de un fragmento `break` en UML.
