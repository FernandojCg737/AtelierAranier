## Notas

- **Los mensajes 5-9 no distinguen que solo se ejecutan si el cache vencio**: en el codigo real, [`mis_recomendaciones()`](/backend/app/api/v1/endpoints/recomendaciones.py#L221) recien llama a `_regenerar_recomendaciones()` (que engloba los mensajes 5-9) si `MAX(fecha)` (mensaje 3) es `None` o tiene mas de `_UMBRAL_REFRESH` = 24 horas (linea [231](/backend/app/api/v1/endpoints/recomendaciones.py#L231)). El diagrama dibuja toda la cadena como si siempre se ejecutara -- mismo hallazgo ya confirmado en `docs/metodos-por-cu/CU18.md` y `docs/Analisis de clases/CU18.md`, ahora tambien en la vista de secuencia.
- El mensaje 5 (`generarCandidatos`) se dibuja como **autollamada** de `:GestorRecomendaciones`, evitando el tipo de error de atribucion que si tenia el diagrama de clases para operaciones equivalentes en otros CUs (ej. CU16) -- pero tambien oculta que [`_generar_candidatos()`](/backend/app/api/v1/endpoints/recomendaciones.py#L74) consulta realmente tres tablas (`venta`/`detalle_venta_*`, `producto`, `inventario`) en un motor de reglas en cascada de 3 niveles, no un calculo sin acceso a base de datos.
- El mensaje 8 (`upsertRecomendacion`) confirma por tercera vez que no existe ningun `sp_upsert_recomendacion` real -- es SQL crudo (`INSERT ... ON CONFLICT DO UPDATE`).
- Igual que los otros dos diagramas de este CU, este tampoco modela la funcionalidad paralela "Tambien te puede interesar" (`productos_relacionados()`, tabla `producto_relacionado`) ni el trigger que marca `convertido = true` cuando una recomendacion termina en compra.
